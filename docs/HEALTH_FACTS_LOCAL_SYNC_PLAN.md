# 健康事实库与本地同步开发计划

状态：已确认的产品方向；**不属于当前 v0.1 工作采集里程碑的实现范围**。
最后更新：2026-08-01

## 1. 目标

Dayday 后续增加一个本地优先的“健康事实库”。它把用户授权读取的、非临床的
Apple Health / HealthKit 数据保存为可追溯的个人档案，供 Dayday 浏览、检索和
主动导出。

产品首先是安静的个人档案馆，而不是健康教练、医疗产品或效率工具：

- 客观呈现事实、来源、时间与趋势；不生成健康分数、生产力分数、诊断或因果解释。
- 原始健康事实、工作事实、日记/情绪是独立数据域。健康数据不得自动进入工作报告、
  日记正文或模型请求。
- Dayday 只读 HealthKit，不回写、不“校正”Apple Health 数据。
- 非临床健康原始记录默认在本地永久保存，直到用户按类型或日期范围主动删除。

## 2. 已确认范围

### 纳入

尽可能读取系统版本、设备、地区和用户授权下可访问的非临床 HealthKit 事实，按实际
可用类型渐进实现：

| 分组 | 例子 |
| --- | --- |
| 身体测量 | 身高、体重、BMI、体脂、腰围 |
| 活动与训练 | 步数、距离、活动/静息能量、站立、锻炼时间、训练 |
| 心脏与循环 | 心率、静息/步行心率、HRV、血压、心率恢复、房颤负荷 |
| 呼吸与睡眠 | 睡眠片段/阶段、呼吸频率、血氧、腕温、睡眠呼吸干扰 |
| 营养与摄入 | 饮水、能量、营养素、咖啡因、酒精 |
| 身体机能 | VO2 max、步态、步行稳定性、跌倒、活动能力 |
| 生殖与主观健康 | 经期、症状、正念、心理状态等；独立授权、默认不在概览展示 |
| 来源与同步 | HealthKit 来源/设备、记录 UUID、记录时间、同步版本和删除变更 |

“完整”指尽可能忠实保存 HealthKit 公开且已授权读取的事实，不承诺复刻 Apple Health
的每个 UI 卡片。某项 UI 指标若没有可读的公开 HealthKit 数据类型，则 Dayday 不伪造或
反算它。

### 排除

- 临床病历、化验、处方、过敏及其他医疗机构 FHIR 记录。
- 心电图波形、听力图、视觉处方、训练路线及其他文档/文件型或高风险明细。
- 健康评分、诊断、治疗建议、提醒/目标打卡、跨域因果推断。
- Dayday 内置的云端通用 AI 发送、MCP、localhost API；这些能力以后另行决策。

## 3. 平台与同步边界

本计划以 iPhone companion 作为 HealthKit 读取端；Mac 主应用不能直接读取 HealthKit
store。因此 iPhone 是健康采集端，Mac 是长期本地档案、浏览和导出端。

```text
Apple Watch / iPhone / 第三方健康来源
                 │
                 ▼
       Dayday iPhone（HealthKit 读取、本地待同步队列）
                 │
        同一局域网的加密点对点传输
                 │
                 ▼
       Dayday Mac（本地 SQLite 健康事实库、展示与导出）
```

- 不使用 iCloud / CloudKit 传输或存放健康事实；不建立 Dayday 服务器，不接入第三方
  同步服务。
- 同一 Wi-Fi 下安静地自动同步；设置页展示设备、覆盖范围、待同步数、上次成功时间和
  可行动错误。提供“立即同步”。
- 自动同步是最终一致、机会型行为：iOS 可能暂停后台 App，不能承诺每一条 HealthKit
  变化即时到达 Mac。iPhone 必须先持久化增量，之后在获得执行机会、打开 App、收到
  HealthKit 更新或用户手动同步时重试。
- USB 直连同步可以作为后续兜底能力，但不是首个垂直切片的前提。

## 4. 数据语义与存储策略

### 4.1 两层数据

`HealthObservation` 是档案真相：保存单条/单段 HealthKit 事实的类型、值/单位或分类
状态、开始/结束时间、记录时间、来源、设备、HealthKit UUID、允许的元数据、同步修订
和删除墓碑。

`HealthDailySummary` 是可重建的阅读投影：依据用户日界线和版本化汇总规则得出当天的
睡眠、活动、训练、身体测量等摘要。它不能取代原始记录。

所有时间保存 UTC 与原始时区信息；展示和日摘要遵循 Dayday 的逻辑日边界。数量数据始终
保存值与原始单位，并额外保存用于比较的规范单位。来源必须可追溯，绝不把来自多设备或
多 App 的样本无依据相加。

### 4.2 同步一致性

- iPhone 使用每种 HealthKit 类型的稳定增量锚点读取新增和删除，锚点、出站批次和接收
  确认都必须持久化。
- 每个事实使用 HealthKit UUID、来源和变更版本幂等合并；不得因重试重复插入。
- 删除是同步事实：Mac 接收到删除后写入墓碑/删除日志，防止旧批次重现已删除的数据。
- 本地删除只删除 Dayday 副本，绝不删除 Apple Health 原始记录。
- 传输协议以版本化 envelope、批次 ID、游标确认、校验和和可恢复重试为基础；核心协议
  和公共类型落地前需要 ADR。

## 5. 安全、隐私与权限

- 首次配对必须由 iPhone 与 Mac 明确确认；配对后保存设备身份和密钥材料到 Keychain。
- 使用 Bonjour 仅发现已配对的 Dayday 服务，随后建立相互认证、加密的点对点连接；不把
  健康内容写入 Bonjour TXT record 或日志。
- iPhone 需要 HealthKit 的细粒度读权限和 Local Network 权限说明；权限按类别逐步请求，
  不在首次启动索取全部类型。
- 高敏感普通健康数据（如心理状态、生殖、房颤负荷）独立开关、独立导出/删除，且默认
  不出现在日概览。
- 设置页必须诚实表达“无记录/未收到数据/历史范围受限/同步失败”，不能把空结果解释为
  用户拒绝权限。
- 不保存临床或文件型排除对象，即使设备或 API 未来可访问它们。
- 数据导出必须为用户主动操作，显式选择类型、日期范围与粒度。初版不代替用户把健康
  数据发送给任何外部 AI 或服务。

## 6. 分阶段开发流程

当前 v0.1 的 `collect -> persist -> Today -> Session/Activity -> BYOK work report` 闭环保持
优先。本计划只在该闭环稳定后启动。

### H0：合同、法规和原型验证

1. 编写 ADR：健康域边界、排除对象、读取/保留/删除语义、工作报告隔离和同步协议边界。
2. 建立 `DaydayHealth` iOS-only 模块；确认现有 `DaydayCore` 不依赖 HealthKit。
3. 用真机小 spike 验证 HealthKit 授权、历史范围、后台更新机会、Bonjour 配对和加密连接。
4. 制作数据类型注册表：SDK availability、是否可读取、敏感级别、展示策略、规范单位和
   聚合策略。注册表不能把“Apple Health 首页可见”误当作“可读取”。

验收：真机不请求临床权限；健康类型、隐私说明、存储和同步边界经 ADR 审核；未进入生产
数据迁移。

### H1：核心事实模型和本地持久化

1. 在 `DaydayCore` 定义闭合的 `HealthObservation`、`HealthDailySummary`、来源、同步状态
   和敏感类别模型；通过 ADR 后再公开。
2. 在 `DaydayStorage` 增加独立的版本化 SQLite namespace、迁移日志、原子写入、墓碑、
   类型/日期查询和按范围删除。
3. 实现可重建日摘要，先覆盖睡眠、步数、训练、体重四类。
4. 实现 CSV/NDJSON/manifest 的只读导出草案；不添加 API 或 MCP。

验收：迁移、幂等插入、源/单位/UTC round-trip、DST 日界线、删除墓碑、类型级删除、导出
往返和工作报告隔离均有确定性测试。

### H2：iPhone HealthKit 采集与本地队列

1. 新增最小 iPhone companion target、HealthKit capability、精确用途文案及 Local Network
   隐私说明。
2. 实现每类型增量锚点、首次历史导入、删除读取、本地加密队列和批次确认状态。
3. 先实现睡眠、步数、训练、体重；覆盖 Apple Watch、iPhone、无数据、有限历史和撤销/变更
   授权的真机行为。
4. 实现 HealthKit 更新触发的机会型同步调度，但任何未完成批次都保留到下一次可执行时机。

验收：断网、杀进程、重复运行、权限变动和 HealthKit 删除后不会丢失、复制或伪造记录；
收集到的健康内容从不写入普通日志。

### H3：配对与局域网增量同步

1. 使用 Network framework + 受限 Bonjour service type 发现本机 Dayday；不扫描任意网络
   服务。
2. 增加用户可验证的首次配对、Keychain 身份、相互认证、加密传输、批次确认和重放防护。
3. Mac 实现接收、校验、事务性落库和对 iPhone 的确认；中断恢复不重放成功批次。
4. 实现安静自动尝试与设置页“立即同步”。

验收：同网自动同步、手动同步、Mac 不在线、iPhone 后台暂停、网络切换、重启、配对失效和
重复/乱序批次均可恢复；健康事实没有离开两台本地设备。

### H3.5：同步概览与真实健康指标首页（已完成，2026-08-09）

1. 保留 iPhone Companion 作为必需的 HealthKit 采集端，继续支持同一 Wi-Fi 自动尝试和手动
   “立即同步”；Mac 端继续承担配对、确认和长期归档。
2. Mac 健康首页直接展示心率、每日步数和每晚睡眠时长；档案总量、来源数、成功批次与最近回执
   收纳到“同步与来源”，不再常规加载或渲染逐条健康事实。
3. 健康热力图固定展示所选指标最近一年真实每日值，并采用共享连续色阶和 Wave Reveal；折线图
   支持当日、7 天、1 个月和全年，悬浮时显示最近数据点的准确值与单位。样本数量与聚合说明只在
   Info 浮层中出现。
4. 统计查询最多覆盖 367 天，在 Storage actor 内使用覆盖索引和预计算时区/DST 分段聚合；连续
   小批次同步后的界面刷新合并执行，避免每批触发全库统计。
5. 已用 20 万条合成档案验证聚合结果和性能；单条读取、完整导出和本机删除能力保留在底层，
   不进入当前健康首页。

心率、步数和睡眠的首批单位、累计/平均/区间及多来源协调口径见 ADR 0105。后续 H4 仍需为其余
健康类型逐项冻结同样的合同并完善导出/删除交互；任何指标都不得被解释为身体状态评分或综合
健康结论。

### H4：档案展示、管理与导出

1. 新增独立“健康”浏览面，而不是改变工作日报输入。
2. 提供日档案、类型详情、长期趋势、来源/覆盖范围和同步状态；高敏感组默认隐藏。
3. 提供类型级与日期级删除、重新导入、CSV/NDJSON/manifest 导出和本地完整备份。
4. 明确显示数据来源、单位、数据空缺和同步时间；不显示综合健康结论或分数。

验收：用户可在不使用 AI 的情况下浏览、验证来源、导出和删除所有已同步数据；删除不会影响
Apple Health，也不会跨入日记或工作报告。

### H5：扩展覆盖与长期稳定性

1. 按数据类型注册表分批加入其余非临床 HealthKit 类型，而不是一次性索取全权限。
2. 对高频记录（心率、呼吸等）测试多年数据量、查询索引、批处理、耗电、存储容量和导出
   性能。
3. 执行至少 14 天真实设备狗粮测试：Watch 采集、睡眠延迟写入、第三方来源、离线恢复、
   升级迁移和用户删除。
4. 仅在上述稳定后，另立提案讨论本机 API/MCP、局部本地模型分析或更广泛外部访问。

验收：没有数据丢失/重复、无未经确认的网络外传、所有高敏感类别的可见性与删除规则正确，
并有可审计的容量与同步健康诊断。

## 7. 模块归属和接口约束

| 模块 | 责任 |
| --- | --- |
| `DaydayCore` | 健康领域值对象、日摘要纯计算、隐私/保留策略、仓储协议 |
| `DaydayStorage` | 独立 SQLite schema、迁移、墓碑、导出与本地备份 |
| `DaydayHealth`（新增） | iOS HealthKit 读取、类型注册表、锚点与本地出站队列 |
| `DaydaySync`（新增或 Integrations 子域） | 配对、局域网发现、加密批次传输、确认与恢复 |
| `DaydayApp` | iPhone 授权/同步状态、Mac 健康档案和设置 UI |

平台服务依赖 Core，Core 不反向依赖 HealthKit、Network framework、SwiftUI 或 SQLite。任何
新增公共类型、存储 schema、同步 wire format、保留/删除策略都必须先写 ADR，并为隐私、
迁移和失败恢复添加测试。

## 8. 非目标与后续决策

- 近期不实现云端同步、Dayday 服务端、通用云端 AI 传送、本机 API/MCP、提醒/目标、评分、
  医疗功能或自动跨域分析。
- 后续若讨论 AI 或外部访问，必须单独评估 HealthKit 对第三方披露的规则、用户授权、数据
  最小化和公开发布合规性；不得由本计划默认授权。
- iPad 阅读端、USB 同步、局部本地模型分析和其他设备平台均为后续独立里程碑。

## 9. 外部约束参考

- Apple HealthKit：Health 数据为敏感个人数据，按类型细粒度授权，应用必须清晰说明用途。
- Apple App Review Guidelines 5.1.3：HealthKit 数据不得用于广告/营销/基于使用的数据挖掘；
  不得将个人健康信息存储在 iCloud。
- iOS 后台执行并不保证持续运行；局域网自动同步必须以持久队列和可恢复重试实现最终一致。
- Bonjour/Network framework 需要本地网络用途说明和受限的服务类型声明。
