# Dayday 产品、设计与开源参考地图

- **用途：** 为参与 Dayday 的 AI 与人工开发者提供可执行的产品设计依据、技术参考边界和
  源码许可证约束
- **状态：** 内部开发规范
- **最近核对：** 2026-08-01
- **适用范围：** 产品规划、界面设计、采集、理解、日报、日记、统计和集成

## 1. 为什么需要这份文档

Dayday 不是在真空中设计的。它吸收了自动时间追踪、桌面工作日志、输入统计、个人数字记忆、
AI 工作总结和原生 macOS 应用中的成熟经验。但“参考产品”可能指四种完全不同的事情：

1. 观察一个产品解决了什么用户问题；
2. 借鉴信息架构、交互节奏或视觉层次；
3. 阅读开源实现以理解一种工程取舍；
4. 直接复制、修改或链接第三方代码。

前三者并不自动授权第四者。本文件要求开发者始终标明参考发生在哪一层，并把外部方案翻译成
Dayday 自己的产品语义，而不是做一个界面拼贴或源码拼装品。

本文件还有第二个目的：让新接手的 AI 不必重新猜测“为什么 Dayday 要有时间线、为什么不做
专注评分、为什么要将日报和日记隔离、为什么只记录聚合输入”。这些取舍来自竞品验证、用户
明确决策和 Dayday 自己的隐私边界。

## 2. 读取和使用规则

### 2.1 哪些任务必须先读本文

以下任务在修改代码或产品文档前必须阅读本文相关章节：

- 主窗口、菜单栏、Today、时间线、统计、历史和设置界面；
- 应用/窗口、屏幕、键盘、鼠标、浏览器和多显示器采集；
- Session/Activity 构造、证据选择和 AI 理解；
- 工作日报、日记、情绪、天气和待办；
- Chrome、Agent、本地 API/MCP 和跨设备设计；
- 引入第三方包、复制外部代码或参考开源实现。

### 2.2 证据等级

每条参考结论使用以下证据等级：

| 等级 | 含义 | 可用于什么 |
| --- | --- | --- |
| O1 | 官方产品站、官方文档或官方仓库当前内容 | 产品事实、当前许可证、公开架构 |
| O2 | 用户实际安装的软件及用户提供截图 | 界面、交互和功能观察 |
| O3 | 已在固定 commit 阅读过的开源源码 | 具体实现参考；必须记录 commit 与许可证 |
| I1 | 基于公开材料的合理推断 | 只能形成待验证假设，不得当作产品事实 |
| U1 | 尚未验证的二手描述 | 不得驱动高风险实现 |

本文当前主要使用 O1 和 O2；`docs/external-sources/O3-20260808-01-dayflow.md` 记录了一次
Dayflow 固定 commit 的 O3 源码研究，且该记录明确说明本次没有复制或翻译外部代码。日记 Markdown
编辑器的 O1/O3 选型记录见 `docs/external-sources/O4-20260809-01-markdown-editors.md`。

### 2.3 参考不等于照搬

AI 在实现前要完成一次“设计转译”：

```text
外部产品解决的问题
→ 用户真正需要的结果
→ Dayday 的产品原则与隐私限制
→ Dayday 自己的数据语义和交互
→ 可验证的实现
```

禁止反向操作：先复制一张竞品页面，再为页面中的每个组件虚构数据和功能。

## 3. 当前源码复用与许可证事实

### 3.1 Dayday 当前状态

截至本次核对：

- Dayday 没有直接复制 Timing、WhatPulse、小黑日报助手、Dayflow、ActivityWatch 或
  Screenpipe 的源码；Dayflow 的固定 commit 源码研究已按 O3 记录，未复制或翻译代码；
- `Package.swift` 没有远程 Swift Package 依赖；
- 运行时主要使用 Apple 原生框架和系统 SQLite；
- XcodeGen 是 MIT 许可的构建期工具，不链接进 App；
- Xcode 项目文件由 XcodeGen 生成；
- 其余 Dayday 源码由本项目 Agents 按自己的契约实现；
- 仓库中没有上述竞品的版权头、vendored 源码或 attribution 义务记录。

### 3.2 外部源码使用规则

任何 AI 在复制、翻译或改写外部代码前，必须先提交一份依赖/来源提案，至少包含：

- 仓库 URL；
- 精确 commit 或 release；
- 文件路径和拟复用范围；
- 当前许可证原文链接；
- 是否允许商业使用、修改、分发和闭源/开源组合；
- attribution、NOTICE、source disclosure 和修改文件义务；
- 为什么不能用 Apple API 或独立实现；
- 替换成本；
- 隐私和供应链风险。

未经批准不得“参考着重写”具体函数。仅改变变量名、语言或文件结构仍可能构成派生代码。

### 3.3 当前参考项目许可证

| 项目 | 当前类型 | 2026-08-01 核对结果 | Dayday 规则 |
| --- | --- | --- | --- |
| 小黑日报助手 | 商业闭源产品 | 产品站声明软件著作权；没有源码许可 | 只观察产品与界面，不使用代码或素材 |
| Timing | 商业闭源产品 | 没有供 Dayday 复用的公开源码许可 | 只参考产品问题与交互原则 |
| WhatPulse | 商业产品 | 官方文档公开功能，不等于源码授权 | 只参考聚合统计表达，不复制素材/代码 |

## 4. 一级产品参考

### 4.1 小黑日报助手

#### 来源与状态

- 官方站点：[小黑日报助手](https://www.xiaoheiribao.com/)
- 证据：O1 官方功能与隐私说明；O2 用户提供的大部分桌面界面截图
- 类型：商业闭源产品
- 代码复用：无

#### 它验证了什么

小黑日报助手验证了“自动记录工作事实 → AI 整理时间线 → 日/周/月报告 → 下一步行动”的完整
产品链条。官方站点公开描述截图、应用活动、主动添加文本/图片/音视频、AI 分类、日报周报月报、
时间线、应用使用、热力图、词云、待办、本地 Agent 和导出备份等能力，并强调核心数据本地
优先、可暂停、可排除敏感应用、可选择显示器、截图默认分析后删除。

#### Dayday 应借鉴

- 不是从“写报告”开始，而是从工作发生时建立素材；
- Today 同时承担运行状态、当天概览和进入详细时间线的入口；
- 将工作时间线、应用记录、时段热力图和历史报告作为互相连接的视图；
- 菜单栏提供低打扰状态和少量高频操作；
- 多显示器是一级事实，而不是一个隐藏设置；
- 用户可以添加主动记录来修正纯自动采集的盲区；
- 报告必须可以编辑、复制、导出和保留历史；
- 本地 API/Agent 是个人数据可组合性的出口；
- 暂停、排除、截图生命周期和本地存储需要被用户看见。

#### Dayday 不应照搬

- 不采用卡片等权、信息块过大的通用仪表盘布局；
- 不将“专注时段”“效率洞察”升级为用户评分；
- 默认日报不依赖固定结构化模板或模板市场；
- 不把待办、日报和个人日记混成一个 AI 工作流；
- 不因为竞品展示“截图分析后删除”就省略 Dayday 自己的内存生命周期、失败清理和容量证明；
- 不复制吉祥物、插图、中文文案、图标组合、页面排版或素材。

#### 对 Dayday 界面的具体转译

| 小黑形态 | Dayday 转译 |
| --- | --- |
| 今日工作概览卡片 | Evidence Thread 起点中的状态、最近事实和简洁日概览 |
| 横向时段格 | Today 使用纵向证据脉络；热力图页再使用紧凑时段格 |
| 已连接显示器卡片 | 多显示器来源细线、状态列表和拓扑详情，不假设只有主屏重要 |
| 应用记录柱状图 | 客观时长、切换和持续前台统计；不显示生产力评分 |
| 模板化报告 | 默认自由形式 AI 草稿，可选自定义指令 |
| 接入 Agent | 后期本地受保护 API/MCP；默认安静，无内置聊天首页 |
| 待办提取 | 作为可确认建议，不能静默创建或声称任务已完成 |

### 4.2 Timing

#### 来源与状态

- 官方站点：[Timing](https://timingapp.com/)
- 官方说明：[Timing FAQ](https://timingapp.com/help/faq)
- 证据：O1
- 类型：商业闭源 macOS 应用
- 代码复用：无

#### 它验证了什么

Timing 验证了高质量自动时间追踪需要将前台应用、窗口标题、文档路径或 URL、空闲时间、项目
归类、人工补录、日历和时间线结合。其公开 FAQ 说明它定期记录当前活动窗口，空闲达到可配置
延迟后暂停跟踪，并允许在时间线填补缺口。它还将时间片限制为最多归属一个项目，从而避免
时长重复计算。

#### Dayday 应借鉴

- 自动采集不要求用户手动开计时器；
- 时间线允许用户填补空白、合并、拆分或纠正活动；
- 采集必须低资源、长期稳定、可随登录启动；
- 原始事实和用户归类分离；
- 同一时间维度应有明确的重叠与去重规则；
- 日历事件可以作为上下文，不应自动等同于实际工作；
- 菜单栏 tracker 和主窗口职责分离；
- 项目/类别规则应可复用，但用户修正优先于自动规则。

#### Dayday 不应照搬

- 不采用 Timing 的 Productivity Score；
- 不把“无键鼠输入”直接解释为离开、发呆或不专注；
- 不把唯一前台窗口当作多显示器环境的完整语义；
- 不按一秒粒度无条件保存所有窗口标题和路径；
- 不默认保存完整 URL、路径或浏览器无痕上下文；
- Dayday 的核心对象是客观 Event、Session、Activity 和证据，不是计费用 timesheet。

#### 工程提示

Timing 的公开采集频率是产品事实，不是 Dayday 的参数要求。Dayday 应采用事件驱动、状态稳定、
冷却和周期性保险刷新相结合的方案，按信息变化价值决定持久化，而不是机械复制一秒轮询。

### 4.3 Dayflow

#### 来源与状态

- 官方仓库：[JerryZLiu/Dayflow](https://github.com/JerryZLiu/Dayflow)
- 产品站：[Dayflow](https://www.dayflow.so/)
- 许可证：MIT
- 证据：O1；O3 源码研究记录见 `docs/external-sources/O3-20260808-01-dayflow.md`，未复用代码

#### 它验证了什么

Dayflow 将轻量屏幕片段交给用户选择的 AI provider，形成按时间排列的 activity cards，并提供
daily standup、weekly review、Markdown export、local-first storage、存储上限和自动清理。
它强调单纯知道“打开了 Cursor 两小时”不够，需要理解具体在开发、调试还是阅读。

#### Dayday 应借鉴

- 应用时长只是最低层事实，工作意义来自多源上下文；
- 屏幕理解应针对稳定、变化有意义的证据，而非逐帧分析；
- AI provider 可选择，本地模型和 BYOK 都是合理路线；
- 用户应看见时间线活动，而不是面对截图仓库；
- Markdown 导出是低成本、高价值的开放出口；
- 需要明确存储预算、自动清理和历史证据过期；
- daily standup 说明“昨天成果、今天重点、阻塞”是有价值的衍生视图。

#### Dayday 不应照搬

- 用户已经决定不做内置 RAG 和工作数据聊天；
- 不做“focus/distraction”判断或标签；
- 不把截图/录屏作为永久主数据；
- 不把 Activity 卡片中的 AI 文本伪装成客观事实；
- 不要求系统音频录制才能完成基础工作日报；
- 不直接复制 Dayflow Swift 源码，即使 MIT 允许，也必须先登记必要性和 attribution。

#### 可研究但尚未采用的工程方向

- 捕获片段选择与去重；
- provider abstraction；
- 本地/云模型切换；
- timeline export；
- 清理策略和磁盘预算。

研究时必须固定 commit，并重点比较 Dayflow 的隐私/存储语义与 Dayday 已接受的 ADR，不能用
外部实现覆盖 Dayday 的负向控制、证据 provenance 或日报/日记隔离。

### 4.4 WhatPulse

#### 来源与状态

- 官方站点：[WhatPulse](https://whatpulse.org/)
- 输入页文档：[Using the Input tab](https://whatpulse.org/help/docs/software/input/using-the-input-tab)
- 隐私文档：[Privacy & Data Collected](https://hub.whatpulse.org/help/docs/faq/privacy-and-data-collected)
- 证据：O1、O2 用户提供的键盘热力图截图
- 类型：商业产品
- 代码复用：无

#### 它验证了什么

WhatPulse 证明键盘和鼠标的“非内容型数量统计”本身也能成为长期个人数据：按键频率、键盘
布局热力图、鼠标按钮、滚动、移动距离、点击热区、应用维度和多时间范围。它公开强调不记录
输入文字和按键顺序，并对输入进行聚合。

#### Dayday 应借鉴

- 将输入统计设计成长期、低成本的客观趋势；
- 键盘热力图支持实际布局，而不是只画固定美式 QWERTY；
- 鼠标热力图按显示器/拓扑区分；
- 同一数据同时提供可视化和数字表格；
- 支持今日、昨日、周、月、年和自定义范围；
- 允许关闭热力图、清理旧数据和重置统计；
- 鼠标距离、点击、滚动和键盘总量分别表达，不合成评分；
- 多显示器拓扑变化需要版本化，否则历史热区会错误叠加。

#### Dayday 与 WhatPulse 的边界差异

WhatPulse 当前文档包含按键组合、每应用输入、每窗口标题输入和鼠标点击坐标等能力。Owner
Deep Capture 接受比早期 Dayday 更丰富的应用、窗口、网页和可见内容，但不会通过原始输入
事件实现内容捕获：

- 不保存字符或按键顺序；
- 不保存组合键历史或可重放序列；
- 不保存精确点击坐标和鼠标路径；
- 可以建立应用维度的总输入量、文字产出量和写作时段，但不保存应用内逐键分布或顺序；
- 不记录可被反推写作内容的分钟级稀疏序列；
- 安全输入、排除应用和非 allowed disposition 必须贡献严格的零；
- 输入层只持久化归一化网格、按钮/滚动/距离总量、按键计数和不可重放的文字产出聚合；
- 网页正文、聊天内容和其他可见文本由认证浏览器扩展、Accessibility、OCR 或专用连接器
  单独采集，经过来源分类与秘密信息脱敏后进入内容/证据归档，不能从键盘序列重建。

#### 界面提示

不要复制 WhatPulse 的高饱和彩虹键盘和厚重多层导航。Dayday 使用统一 Mineral 语义色、连续
数值色阶、清晰图例，并提供排序表格。热力图是统计视图，不应成为 Today 的主视觉焦点。

### 4.5 ActivityWatch

#### 来源与状态

- 官方仓库：[ActivityWatch/activitywatch](https://github.com/ActivityWatch/activitywatch)
- 官方站点：[ActivityWatch](https://activitywatch.net/)
- 许可证：MPL-2.0
- 证据：O1；当前未登记 O3 源码复用

#### 它验证了什么

ActivityWatch 验证了本地数据所有权、跨平台 watcher、活动窗口、浏览器扩展、AFK watcher、
本地 server/Web UI 和可扩展 API 的长期可行性。其架构将 watcher、server、UI 和同步分开，
watcher 通过 heartbeats 向本地服务报告事实。

#### Dayday 应借鉴

- Collector/Watcher 应模块化，失败不拖垮整个系统；
- 采集器只报告自己的客观事实，不直接生成产品结论；
- 本地存储和查询 API 有利于长期可扩展；
- 浏览器上下文适合通过独立扩展获取；
- collector identity、heartbeat/interval、去重和数据桶值得研究；
- Windows 后期可以复用相同 Core 语义、替换平台采集器；
- 用户应拥有数据、导出和清理权。

#### Dayday 不应照搬

- App 内部当前不需要以 localhost server 作为所有模块的强制总线；
- 不把 AFK 当作“没有工作”或“不专注”；
- 不使用未经认证的浏览器 watcher 数据；
- 不保存完整 URL 和窗口标题而缺少 Dayday 的隐私分类；
- 不直接复制 MPL 文件进入 Dayday，除非接受并履行文件级源码义务；
- Dayday 的 Event/Session/Activity provenance 和负向边界比通用 heartbeat 更严格。

#### 未来源码研究规则

如果要研究 watcher 心跳、bucket 查询或本地 API，只能先做 O3 登记：固定仓库和 commit，说明
阅读的文件、学到的抽象、Dayday 的独立实现差异。不要边看外部函数边逐行翻译。

### 4.6 Screenpipe

#### 来源与状态

- 官方仓库：[screenpipe/screenpipe](https://github.com/screenpipe/screenpipe)
- 当前许可证：[Screenpipe Commercial License](https://github.com/screenpipe/screenpipe/blob/main/LICENSE.md)
- 证据：O1
- 类型：source-available，不应再称当前主分支为 MIT 开源
- 代码复用：禁止使用当前源码构建或集成竞争产品

#### 它验证了什么

Screenpipe 的公开设计强调事件驱动捕获、Accessibility tree 优先、OCR fallback、屏幕/音频到
本地 AI 记忆、过滤规则、资源预算和 Agent 接入。它公开指出通过应用切换、点击、输入停顿和
滚动等有意义事件触发截图，可以减少大量重复帧。

#### Dayday 只借鉴高层思想

- 屏幕不是唯一信号，AX 结构化上下文通常比 OCR 更便宜；
- OCR 应是 fallback 或补充，不是每个周期的默认操作；
- 变化检测、稳定窗口和冷却能降低 CPU、磁盘和模型成本；
- 采集系统必须公开资源预算；
- exclusions 必须在内容进入持久层前生效；
- Agent 接口可以让用户拥有的数据参与外部工作流。

#### Dayday 明确拒绝

- 不追求 24/7 全屏和全音频“记录一切”；
- 不做可搜索的截图/音频永久记忆库；
- 不持久化完整 Accessibility tree；
- 不在 v0.1 采集麦克风或系统音频；
- 不做内置 RAG/聊天；
- 不接受每月数十 GB 作为默认资源成本；
- 不复制、翻译、链接或嵌入 Screenpipe 当前源码。

Screenpipe 仅作为“怎样从屏幕获得上下文”和“资源成本为什么必须事件驱动”的产品参考。

### 对 Dayday 的约束

- 优先使用 `MenuBarExtra`、`NavigationSplitView`、系统按钮、菜单、表单和辅助功能环境；
- 菜单栏从上到下放最重要、最高频、最需要快速确认的内容；
- 分隔线只分隔逻辑组，不把每个数据点做成独立卡片；
- 权限请求发生在用户能理解原因的时刻；
- 密钥使用 Keychain，不放普通文件或数据库；
- 图表数据是主角，轴和装饰退后；
- 颜色不能是区分事实、推断、修正或错误的唯一手段；
- 每个重要图表有文本、键盘和 VoiceOver 等价入口；
- 小文字默认满足 4.5:1 对比度，非文字关键图形满足 3:1；
- Reduce Motion 下用短淡入或静态变化替代空间移动；
- Reduce Transparency 下使用实色表面；
- 原生材质只用于菜单栏、瞬时控件和浮层，不覆盖工作台内容页；
- 动画用于解释状态变化，不用于制造“高级感”。

当竞品界面与 Apple 原生交互冲突时，Dayday 默认遵循 Apple 规范和用户已冻结的设计系统。

## 6. 跨产品综合结论

### 6.1 Dayday 的独特定位

Dayday 不是以下任意一种产品的免费复制版：

- 不是 Timing 的免费 timesheet；
- 不是 WhatPulse 的键鼠统计克隆；
- 不是 Dayflow 的聊天式屏幕日志；
- 不是 ActivityWatch 的 Swift 重写；
- 不是 Screenpipe 的轻量版；
- 不是小黑日报助手的换皮版本。

Dayday 的组合价值是：

```text
本地、可审计的客观工作事实
+ 多显示器和隐私边界
+ 可解释的 Session/Activity
+ 用户修正权
+ 安静的 BYOK 自由形式工作日报
+ 独立的个人日记
+ 长期非内容型个人统计
```

### 6.2 数据采集语法

从参考产品综合后，Dayday 采用以下原则：

1. **事件驱动优先。** 应用切换、窗口变化、显示器变化、交互状态和系统边界触发观察；周期
   轮询只是保险。
2. **结构化信号优先。** App/AX/可信浏览器上下文优先于 OCR，OCR 优先于视觉大模型。
3. **多显示器独立。** 前台输入显示器不是唯一有意义的显示器；参考屏和媒体屏仍是客观上下文。
4. **负向边界优先。** 暂停、禁用、锁屏、睡眠、权限撤销、secure input 和排除先关闭入口。
5. **原始数据短命。** 原始 frame、bundle ID、AX 值和平台回调不离开 Capture 内存边界。
6. **聚合输入不可重放。** 键鼠数据不能恢复用户写过的内容和操作顺序。
7. **事实不等于意图。** “Chrome 前台 20 分钟”是事实，“研究某方案”是推断。
8. **没有专注真值。** 活跃输入和持续查看可以同时发生，也都不能证明主观专注。

### 6.3 理解与 AI 语法

- Session 首先由时间连续性、来源和硬边界构造；
- Activity 可以跨应用和显示器，但必须保留来源；
- AI 输出是带 provenance 的 provisional inference；
- 置信度用于调试、证据展开和风险控制，不用于给用户打分；
- 用户修正生成新层，不修改 ObjectiveEvent；
- 模型能力增强时可以减少固定模板，但不能放松输入 allowlist；
- 工作日报默认自由表达，支持自定义指令，不以模板市场为核心；
- 日记原文不自动润色，AI 版本永远是可选副本；
- 产品默认安静，不在首页放 AI 对话框，不主动打断用户。

### 6.4 视觉语法

- 主方向是纵向 Evidence Thread，而不是横向甘特图或 KPI 仪表盘；
- Today 是信息密集但有秩序的工作台，不是大面积空卡片；
- 状态和最近事实位于时间线起点，不与时间线争夺主视觉；
- 客观事实用实线刻点，Session 用连续跨度，推断用虚线/半透明覆盖，边界用断口；
- 多显示器用平行来源线或明确 source label，不伪造成单一屏幕叙事；
- 只对低频、确认的新事实做来源可见的轻微入场；
- 高频键鼠事件不逐个动画；
- Activity 默认原位展开，宽窗口才提供侧边 inspector；
- outline icon 默认，filled icon 只表示真实状态；
- Mineral 只是可替换主题，组件只能消费语义 token；
- 应用自有的纵向与横向滚动容器统一使用安静的主题化浮层指示器：透明轨道、约 4 pt 可见滑块，
  颜色来自当前主题的 action token；保留系统滚动物理、触控板手势、原生点击区域与“始终显示滚动条”
  辅助功能偏好，不用装饰性轨道制造额外视觉层级。

## 7. 页面级 AI 设计指令

### 7.1 菜单栏

目标：三秒内回答“Dayday 是否在安全记录、最近有没有事实、我现在能做什么”。

顺序：

1. 当前运行状态和原因；
2. 权限/同意/暂停等记录条件；
3. 最近 60–90 分钟紧凑概览；
4. 最近一条客观事实；
5. Quick Record；
6. Open Today。

禁止：完整仪表盘、长设置列表、多个未实现按钮、AI 聊天框、生产力分数、炫技动画。

### 7.2 Today

目标：重建今天发生了什么，并让用户快速发现缺口或错误。

必须包含：

- 工作日边界；
- 真实运行状态；
- 纵向 Evidence Thread；
- objective fact、Session、inferred Activity、user correction；
- 生命周期断点；
- 多显示器来源；
- 工作概览和可核对的客观汇总；
- 快速记录和日报入口。

历史事实不能因为当前暂停或权限不足而消失。加载状态、数据状态和 collector health 分开建模。

### 7.3 工作时间线与 Activity 详情

- 时间顺序不可打乱；
- 活动跨度必须能追溯成员事实；
- 展开后显示“观察到什么、为什么这样归类、哪里存在冲突”；
- 允许改名、拆分、合并和纠正；
- 用户修正后仍能查看原始推断；
- 不直接展示原始敏感 frame；
- 证据过期时显示“按策略过期”，不让引用悄悄失效。

### 7.4 应用记录

- 显示应用时长、前台区间、切换次数和最长连续区间；
- 分类是用户或推断层，不改变原始应用事实；
- 浏览器可信上下文可进一步拆分域名，但不保存 query/fragment；
- 支持日/周/月和自定义范围；
- 排名不是价值判断；
- 不用红色羞辱娱乐或沟通应用。

### 7.5 时段与输入热力图

- 采用单一连续强度色阶和清晰图例；
- 每个图有数字/表格等价视图；
- 键盘按真实 layout 渲染；
- 鼠标按 topology revision 和显示器分层；
- 显示总量、趋势和分布，不解释主观状态；
- 禁止“高输入=高生产力”“无输入=发呆”的文案。

### 7.6 工作日报

- 默认入口展示当天可用事实范围和生成状态；
- 与日记共用同一套原生响应式 Markdown 写作画布、实时预览、格式菜单、链接编辑和可读性参数，避免两个文字产品形成不一致的输入体验；编辑器滚动容器占满详情区，滚动条贴近详情区最右缘，正文在容器内部保持居中可读列，窄窗口只收缩正文而不把滚动条卡在正文列边缘；日报只在该写作底座上增加工作事实驱动的 AI 生成、重新生成、显式保存和定稿操作，不再提供或提交日报页工作笔记；
- 默认自由形式总结，不要求选择模板；
- 自定义指令是高级可选项；
- 没有 AI 草稿时也允许从空白页直接手写并保存首版；编辑中的正文保存到独立、仅限本机的工作副本，并在页面切换前强制刷新，因此导航或重启不会丢失文字；普通自动保存不产生 revision，只有用户明确“保存版本”、AI 生成或重新生成才形成新版本；
- 生成后进入可编辑草稿，不直接定稿；
- 保留 revision、model、生成时间、usage 和 source references；
- 支持复制、Markdown 导出和历史；
- 不读取日记正文、日记附件、日记位置或情绪数据；日报页可展示天气定位同时解析出的当前地点名称，但该名称只用于界面上下文，不进入模型请求；共享视图组件不等于共享数据上下文；
- 失败时说明 provider、网络、Key 或上下文问题，日志不泄漏 Key/prompt。

### 7.7 日记

- 独立于工作日报，无先后依赖；
- 一天可以多次追加；
- 原文优先、自动保存；
- 空白提示由 MarkEdit 编辑事务直接驱动，首个组合中或已提交字符出现时立即消失，不依赖 1.5 秒
  的 SwiftUI 自动保存同步；这样提示反馈即时，同时不削弱中文输入法的隔离与防卡顿策略；
- Markdown 写作语法使用当前应用主题的 action token：标题、列表标记、引用标记、链接、任务标记、
  插入光标、选区和分隔线随蓝色、紫色、玫红或珊瑚主题切换；代码语法颜色仍保留 MarkEdit 的
  独立语义色，避免把不同 token 强行染成同一颜色；
- 错词、语气词和停顿属于个人表达，不自动修复；
- 天气和情绪是辅助上下文，不是强制字段；
- AI 整理/润色/续写生成独立版本；
- 界面偏阅读与写作，不复制工作台统计密度。
- Apple 手记的按日期回顾、全文搜索、地点视图、附件删除与连续记录统计可作为本机日记的交互参考；不采用其活动数据建议，避免扩大 Dayday 的数据边界。

### 7.8 Settings 与隐私

- 每项采集器独立说明收集什么、不收集什么、用途和系统权限；
- 产品同意与 TCC 状态分开展示；
- 暂停、禁用、排除、保留周期和清理容易找到；
- 危险清理操作显示精确范围和恢复可能；
- API Key 只展示存在/缺失和验证状态；
- 资源页展示 CPU、磁盘、模型调用与保留策略的客观统计。

## 9. AI 实现前检查表

每个实现任务开始前，AI 必须回答：

1. 这个功能参考了哪个产品解决的什么问题？
2. 是产品启发、视觉启发、架构研究还是代码复用？
3. 如果涉及开源源码，精确 commit 和许可证是什么？
4. Dayday 采用了什么，明确拒绝了什么？

6. 是否会记录被禁止的数据或让原始数据活得更久？
7. 多显示器、工作日边界、暂停和权限撤销怎样处理？
8. UI 是否明确区分真实、示例、空状态和未接入？
9. 是否引入生产力/专注价值判断？
10. 是否有文本、键盘和 VoiceOver 等价路径？
11. 失败时是否保持旧事实可见、停止危险 producer 并提供修复说明？
12. 是否能用 Dayday 自己的类型和 Apple API 独立实现？

如果不能回答第 2 或第 3 项，不得粘贴外部代码。
