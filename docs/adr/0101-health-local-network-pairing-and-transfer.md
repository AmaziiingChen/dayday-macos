# ADR 0101: 健康事实的本地网络配对与传输

- 状态：接受
- 日期：2026-08-09
- 关联：ADR 0021、0022、0023、0100

## 决策

Dayday Health Companion 与 Mac 健康档案使用 Network framework 的受限 Bonjour 服务
`_dayday-health._tcp` 发现同网设备；Bonjour TXT record 不包含用户健康内容、设备历史或
配对凭据。首次配对由用户在 Mac 健康页面明确生成，并在需要时显式显示、复制一个 256 位随机
本机设置码，再在 iPhone Companion 中明确粘贴确认。

设置码只在配对时通过用户选择的设备间剪贴板传递，不会写入日志、偏好设置、SQLite、Bonjour
记录或 Dayday 服务端。它在撤销配对前持续有效，不被误称为“一次性”；Mac 重开后默认隐藏，
必须由用户再次显式显示。两端将其保存为 `WhenUnlockedThisDeviceOnly` 钥匙串项。后续传输以
该随机值和配对 UUID 作为 TLS 1.3 PSK 及身份；撤销任一端配对会删除该钥匙串项，之后必须重配。

每一条连接最多传输一个、长度限制为 8 MiB 的 JSON `HealthArchiveBatch`，包含稳定批次 UUID。
Mac 必须在 SQLite 原子应用批次后才回发 `HealthSyncAcknowledgement`；iPhone 只在确认的来源和
批次 UUID 都匹配时，才删除对应的持久化出站变更。连接失败、Mac 不在线、授权未完成或 App
被系统暂停时，iPhone 不删除变更，等待下次手动同步、前台启动或 HealthKit 增量读取后的机会。
首次授权后的初始读取计划同样保留到每个选定类型完成一次锚点核对；前台重新打开后会自动续跑，
不要求用户重新授权或重建队列。

两端都必须显示可核对、但不泄露健康内容的传输状态：iPhone 展示读取等待、待同步数量、当前批次、
成功确认或安全失败原因；Mac 展示等待连接、接收中、已落库的事实/删除记录数量或未完成连接。Mac
仅在 SQLite 原子落库后显示“已写入”并刷新档案，状态中不包含设备地址、健康值、来源名称或配对材料。

## 后果

- 传输不依赖 iCloud、CloudKit、第三方服务、MCP 或互联网。
- 已确认批次重发不会重复入库；未确认批次保留；删除墓碑和事实同样通过该通道传输。
- 同一来源的未确认连续修改会在 iPhone 的出站批次中合并为最终状态，避免“先新增后删除”使
  已删除事实在 Mac 重现。
- 当前实现面向一个用户的一个 iPhone Companion 和一个 Mac 档案。多 iPhone、iPad 或多 Mac
  必须增加独立设备清单和撤销界面，不能共享或复制现有钥匙串凭据。

## 非决策

- 这不引入云同步、局域网 HTTP API、远程访问或自动外部导出。
- 这不允许把临床、文件型、路径或其他排除健康对象纳入传输。
- TLS/Bonjour 可编译不等同于真机本地网络许可已被用户批准；真机测试应在 iPhone 前台完成
  首次本地网络提示和一次手动同步后，再观察机会型自动重试。
