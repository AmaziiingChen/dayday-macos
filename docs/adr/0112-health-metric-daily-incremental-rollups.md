# ADR 0112: 健康指标每日增量汇总

- 状态：接受
- 日期：2026-08-11
- 关联：ADR 0100、0103、0104、0105、0107、0108

## 背景

ADR 0104 已将事实数量和每日记录密度改为持久化增量汇总，但 ADR 0105 的健康指标数值仍在每次
冷查询时从原始 JSON payload 聚合。仪表盘目录扩展到 51 类以后，一次年度刷新最多会执行每类的
日级和细粒度范围查询。结果虽然有界，成本仍会随一年内原始样本数增长，不符合健康页静止和重复
进入时尽量接近零持续开销的目标。

## 决策

健康 schema v5 新增可重建的 `health_archive_metric_daily_rollups`：以“时区、本地自然日、健康
类型”为主键，只保存该类型既有客观投影口径产生的 value、minimum、maximum 和贡献样本数。
`health_archive_metric_rollup_states` 记录各时区投影对应的 archive revision。该决定仅替代
ADR 0105 的“健康数值投影不持久化”实现选择，不改变其单位、来源协调、睡眠会话、缺失值或客观
展示合同。

schema v5 同时为既有每日记录数汇总增加可恢复构建进度。v3 到 v4 迁移只创建统计对象和空状态，
不再在 repository 初始化期间执行类型、来源或每日全表分组。首次 dashboard 使用专用索引做请求
范围内的有界 fallback，并启动基础 totals、每日记录数和每日指标值三个 `.utility` 单飞任务。
每日记录数与指标值均按闭集健康类型逐片提交进度，每片后让步约 20 毫秒。

同步批次、同 UUID 更新、HealthKit tombstone 和本机删除在原始事实写事务内收集受影响的
“日期×类型”单元格。若当前时区汇总与写入前 revision 一致，只删除并重建这些单元格，然后将
汇总 revision 与新的 archive revision 一起提交。没有事实的日期不插入行，不把缺失补成零。
睡眠阶段可能归入次日结束的会话，因此睡眠变更额外失效次日单元格，并用有限回看窗口重建。

类型总数、来源总数和全档案时间边界在正常 apply/delete 中使用 batch delta 维护，不再对每个受
影响类型或来源执行 `COUNT(*)`，也不再每批执行 `MIN/MAX`。只有删除或移动当前极值时，才使用
`(ended_at)` 或 `(kind, ended_at)` 索引的 `ORDER BY ... LIMIT 1` 修补。旧库若在基础统计完成前
收到 mutation，mutation 等待同一个 utility 单飞任务，不在自己的事务入口同步发起全表重建。

年度指标查询将完整自然日从汇总表读取；请求首尾不足一天的区间仍按精确时间边界查询原始事实。
最近七天的 5 分钟或 15 分钟细粒度投影继续使用 `(kind, ended_at)` 索引做短范围查询，不持久化
高频时间桶。睡眠会话需要跨查询日边界的上下文且事实天然稀疏，继续按最多 367 天范围做一次索引
查询；先有限回看 36 小时完成 sessionization，再只输出请求日期，避免丢失在 `startsAt` 前结束
但属于同一跨午夜会话的阶段。最近样本继续使用同一索引和
`LIMIT 1`。因此普通浏览不扫描无关类型或全历史原始表，且不会以大规模细粒度缓存换取交互速度。
睡眠每日汇总不再写入 metric rollup，避免维护一个读取路径永远不会采用的重复投影。

## 迁移与恢复

v4 到 v5 的迁移只创建空汇总表和状态，不在打开 SQLite 文件的迁移事务中解析全部健康 payload。
某时区首次请求仪表盘时，读取路径先用最多 367 天的索引范围查询返回真实结果，然后启动单飞的
`.utility` 后台任务。任务一次只重建一个明确指标并提交进度，指标之间让步约 20 毫秒；状态保存
目标 revision 和下一指标序号。进程中断、同步插入新 revision 或单片失败后，下次请求从可验证
进度继续或安全重启，不会把半成品当成当前汇总。已有 App 层快照继续在回填期间承担立即展示职责。
任务取消停在最近一次已提交分片；repository 重开后从持久化序号继续。回填期间发生 apply 或
delete 时，旧 target revision 永远不能被读取为 current，任务按新 revision 确定性重建。

首次重建成本随原始事实量增长，但只发生一次；之后同步只重建批次实际影响的少量单元格。不同
时区仍各自拥有 revision，切换时区不会误用旧日期边界。

2026-08-11 补充：开发中的一个短暂 v5 构建先写入了指标汇总对象，随后同版本代码又加入每日记录数
回填进度表，造成已经落盘的 v5 指纹与当前定义不一致。修复将当前 schema 正式提升为 v6：v5→v6
事务只验证已知 v5 精确指纹、创建缺失的 `health_archive_daily_rollup_build_states` 空表、记录迁移并
更新元数据。它不扫描、改写或删除原始健康事实。对于曾经写出完整对象集但仍标记为 v5 的短暂
开发构建，也只在完整 schema 校验通过后升级版本，拒绝任何未知 v5 形状。

## 隐私与事实边界

新表位于既有受保护本机健康 SQLite，不新增网络、云端、遥测、AI 或跨域关联。原始
`HealthObservation` 仍是唯一真相；汇总可以全部删除重建，不能反向写入、删除或补造原始事实。
汇总不保存来源名称、设备详情、配对材料、日记、工作事实或诊断结论。

## 性能门禁

- 日级读取使用 `(time_zone_identifier, kind, logical_date)` 索引；返回点数最多受 367 天合同限制。
- 页面范围切换只消费既有 `HealthArchiveDashboard`，不触发重建。
- 当前自然日最多对选中类型执行单日原始范围查询；细粒度查询最多覆盖最近七日。
- 20 万条真实 quantity payload 旧档案的计时必须覆盖 repository init 与首次 dashboard；schema
  打开阶段不得回填 totals、每日记录数或指标值，init + fallback 保持 10 秒宽门槛，
  同 revision 的热查询保持 1 秒门槛。
- 测试必须覆盖同 UUID 更新、tombstone、本机删除、缺失日期、旧 schema 迁移和时区 revision。

## 后果

健康页完整自然日的查询成本主要随天数与展示类型数增长，而不随同日心率等高频样本数增长。代价是
同步事务会为受影响日期执行少量有界重算，并增加本机可重建数值表；细粒度投影仍按需计算，以控制
磁盘、写放大和常驻内存。
